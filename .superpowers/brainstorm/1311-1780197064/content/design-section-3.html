设计方案 — 第 3 部分：数据模型与 API

数据库 Schema 和 REST API 设计

SQLite 数据模型

4 张核心表
projects — 项目
id PK | name 名称 | source_image 原图路径 | rows 行数 | cols 列数 | palette_id 色卡 | color_limit 颜色上限 | status 状态 | created_at | updated_at
cells — 每个格子的颜色和状态
id PK | project_id FK | row 行 | col 列 | color_no 色号 | rgb 颜色值 | completed 是否完成
palettes — 色卡定义
id PK | brand 品牌 | color_no 色号 | name 颜色名 | hex HEX值 | rgb RGB值
edit_history — 编辑历史（用于撤销/重做）
id PK | project_id FK | action 动作类型 | data JSON 详情 | created_at

REST API 设计

GET /api/projects → 项目列表
POST /api/projects → 创建项目（上传图片 + 参数）
GET /api/projects/:id → 项目详情（含 cells）
PUT /api/projects/:id → 更新项目（名称、参数）
DELETE /api/projects/:id → 删除项目
PUT /api/projects/:id/cells → 批量更新格子（编辑时自动保存）
GET /api/projects/:id/stats → 色号统计
GET /api/palettes → 色卡列表
POST /api/export → 导出（生成 PNG/PDF）

关键设计决策

1. 图片存储：用户上传的原图和生成的图纸存在 /public/uploads/，数据库存路径。MVP 不引入对象存储。

2. cells 存储：50×50 = 2500 行，100×100 = 10000 行。SQLite 完全能胜任，但查询用 project_id + row + col 联合索引。

3. 编辑历史：每次单格/批量编辑记录一条 history，前端维护撤销栈指针，支持 50+ 步撤销重做。

4. 自动保存：编辑器中每次操作后 debounce 1s 自动调用 PUT /cells 保存到后端。
